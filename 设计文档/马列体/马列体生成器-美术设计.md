# 马列体生成器 — 设计笔记

> 记录本轮迭代中反复踩坑后沉淀的经验，供后续开发参考。
> 2026年8月

---

## 1. 视觉设计

### 1.1 构成主义不是调 CSS 参数

调阴影模糊度、圆角半径、色板明度——这些是"美化"，不是"设计语言"。构成主义的核心主张是**材料即表达**：

| 对的 | 错的 |
|------|------|
| 颜色承担结构角色（红=立场，黑=重量，金=紧张） | 把红/黑/金当"配色方案"撒在页面上 |
| 硬阴影 `5px 5px 0 #1a1a1a`（套色印刷的偏移感） | `rgba(0,0,0,0.12)` 软阴影（杂志美学） |
| `border-radius: 0`（几何即语言） | 圆角 4-8px（"让卡片看起来友好"） |
| 斜切 `clip-path: polygon(...)`（打破矩形） | 标准矩形卡片排列 |
| 网点纹理 `radial-gradient`（印刷质感） | 纯色背景 |

教训：**先弄清楚你要引用什么美学传统，再动手写 CSS。** 不要从"调个好看的阴影"开始。

### 1.2 卡片宽度必须约束

问题：卡片默认撑满 `max-width: 1200px` 的 container，在大屏幕上像"赤道那么宽"。

修复：所有输出卡片统一 `max-width: 720px` + `margin: 0 auto`。视觉平衡来自**舒适的内容宽度 + 呼吸的留白**。

### 1.3 固定高度 vs 自适应高度

问题：多页卡片切换时，每页内容量不同 → 卡片高度跳变 → 箭头/按钮位置抖动 → 严重的交互劣化。

修复：`height: 600px` 固定死。内容溢出用 `overflow-y: auto` 滚动。箭头 `top: 50%`、圆点 `position: absolute; bottom: 10px`——全部相对于固定高度的父容器定位，不受内容影响。

结论：**多页切换的容器，高度必须固定。** 宁可留白或加滚动条，也不能让骨架动。

## 2. 翻页/切换

### 2.1 translateX 长条方案（错）

做法：把所有页面平铺在一个宽 flex 容器里 → `overflow: hidden` 遮罩 → 点击切换时 `translateX` 移动整个长条。

问题：
- 微调"一段距离"需要反复试错
- 遮罩对不齐时露出相邻页面内容
- 页数增加时更脆弱

### 2.2 独立页面 + 显隐 + 入场动画（对）

做法：
- 每个页面独立的 DOM 元素
- 仅当前页 `display: block`，其余 `display: none`
- 切换时：隐藏旧页 → 新页显示 + CSS `@keyframes` 入场动画（`translateX(24px) + opacity`, 0.3s）

优点：
- 不需要精确计算位移距离
- 不依赖遮罩裁切
- 页数和内容量变化不影响稳定性

结论：**切换（tab/翻页/轮播）的 DOM 结构应该是"容器 + N 个独立子面板"，不是"一个长条"。**

## 3. Canvas vs HTML/CSS

### 3.1 Canvas 的问题

- 暗色模式：Canvas 在 JS 中渲染，必须手动检测 `body.classList.contains('dark-mode')` 并切换颜色。**CSS 变量无法穿透 Canvas。**
- 响应式：需要 `devicePixelRatio` 换算、`resize` 事件监听重绘
- 点击交互：需要手动计算 `getBoundingClientRect` + 坐标映射
- 文本排版：没有自动换行，需要 `measureText` 手动分行
- 调试：Canvas 内容是像素，F12 看不到结构

### 3.2 HTML/CSS 的优势

- 暗色模式：CSS 变量自动切换，零 JS 干预
- 响应式：CSS Grid/Flexbox 自动适应
- 点击：原生 DOM 事件
- 文本：原生排版引擎
- 调试：DOM 结构可见

### 3.3 什么时候用 Canvas

- 分享卡片（需要导出图片——Canvas 是正确选择）
- 雷达图（简单几何图形，Canvas 够用）
- 复杂的自定义数据可视化（ECharts/D3 太重时）

### 3.4 什么时候不用

- 泳道图/时间轴：HTML + CSS 定位更稳定
- 任何包含文本排版的内容：交给浏览器引擎
- 需要暗色模式适配的交互元素

## 4. 规则引擎

### 4.1 规则数据加载

问题：`fetch()` 在 `file://` 协议下被 Chrome 拦截（CORS）。

方案演进：
1. ❌ `fetch('../../js/rules.json')` → file:// 拦截
2. ❌ JSON 内联到 HTML `<script>` → 中文引号 `""` 被转成 `""` 切断 JSON
3. ✅ 外部 JS 文件 `rules-data.js` → `<script src>` 加载不受 CORS 限制

结论：本地开发的静态数据，**用 JS 文件赋值给 `window` 全局变量**，不用 fetch。

### 4.2 规则模板质量

手工编写的规则有两个问题：
- **占位符溢出**：模板用了 `[B]` 但正则只捕获了 1 个组 → 输出里残留字面 `[B]`
- **覆盖率低**：46 条规则分布在 5 导师 × 4 维度 → 单篇输入只命中 0-5 条

解决方向：AI 蒸馏方案——用 LLM 批量从经典文本中提取规则，结构化 JSON Schema 约束输出格式，人工审核后入库。

### 4.3 引擎架构正确性

四阶段管线（词汇→句法→修辞→逻辑）+ 优先级冲突解决 + 已占用区间排除——这个架构是正确的。问题只在数据质量。

## 5. 交互节奏

### 5.1 先让核心流跑通，再加装饰

本次迭代的顺序问题：
1. 先花大量时间在泳道图（数据可视化）上，但规则引擎还没跑通
2. 视觉设计反复修改但核心功能（输入→转换→输出）一直没验证

正确节奏：
1. 核心功能链条（输入→转换→输出对比）先跑通
2. 视觉基底确立（配色、字体、卡片风格）
3. 输出层（诊断、分享、溯源）逐项加入
4. 数据可视化（导师剖面等）最后做——它依赖前三个都稳定

### 5.2 用户反馈的优先级

每次收到反馈时先问：这是**功能 bug**（规则没生效）、**设计问题**（卡片太宽）、还是**体验瑕疵**（切换抖动）？按这个顺序修，不要跳。
