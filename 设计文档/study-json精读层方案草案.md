# study-json 精读层方案草案

> 作用：讨论文章页各个精读 Tab 是否应从 HTML 中拆出，以及如果拆出，应该如何与 `articles-json` 分层。
> 当前状态：`实践论` 已完成单篇 `study-json` 试点，本文保留为分层原则与后续推广依据。

---

## 一、先说结论

当前建议不是立刻把所有精读内容全面 JSON 化，而是采用：

> **正文先稳定，精读后分层；能结构化的先结构化，强布局内容暂留 HTML。**

具体判断：

1. `data/articles-json/` 继续只负责正文层。
2. 若要拆分精读内容，优先新建独立的 `data/study-json/`。
3. 不建议把精读内容直接并回正文 JSON，避免一个文件既存权威正文，又存编辑型解读。
4. 第一阶段只考虑把轻结构 Tab 拆出，不急着处理复杂可视化 Tab。

---

## 二、为什么不建议把 Tab 一口气全塞进正文 JSON

正文和精读内容不是一类东西。

### 1. 正文层的性质

正文层具有：

- 权威文本属性
- 强一致性
- 可被下载、检索、复用
- 更新频率低、边界清楚

这正适合 `articles-json`。

### 2. 精读层的性质

精读层通常具有：

- 编辑性解释属性
- 展示形态差异大
- 迭代频率更高
- 某些文章不完整也可以先上线

如果把两层揉在一个 JSON 中，后果通常是：

- 文件越来越肥
- 维护边界变模糊
- 正文校验与精读校验混在一起
- 将来只想修改一条读法提示，也得碰正文源文件

因此，**正文层与精读层分文件，比混一个文件更清楚。**

---

## 三、哪些 Tab 适合优先 JSON 化

适合先拆出的，是“内容块明显、布局要求不强”的部分。

### 第一批推荐

1. `reading` 读法提示
2. `difficulty` 难点解析
3. `dialogue` 对话空间
4. `action` 行动实验
5. `further` 延伸阅读

这些部分大多可以抽象成：

- 标题
- 若干条目
- 每条有标题 / 正文 / 标签 / 链接

属于典型的轻结构内容。

### 暂不建议第一批 JSON 化的部分

1. `visual` 一目了然
2. `puzzle` 理论拼图

原因不是它们永远不能 JSON 化，而是这两类部分常常包含：

- 图表容器
- 自定义布局
- 时间轴
- 关系卡片
- 理论树
- 复杂的样式语义

如果现在强行统一，很容易为了结构化而结构化，最后变成又大又别扭的 JSON。

---

## 四、推荐目录

建议新增：

```text
data/study-json/{Mentor}/{slug}.json
```

例如：

```text
data/study-json/Mao/shi-jian-lun.json
```

理由：

- 与 `articles-json` 的导师分层保持一致
- 不再引入星级维度，因为精读层和正文评级不是一回事
- 一个精读页通常只对应一个 `slug`

如果后续确实需要共享片段，再另设公共片段层，不要提前设计过重。

---

## 五、推荐字段草案

一个最小可用版本可以长这样：

```json
{
  "title": "实践论",
  "mentor": "Mao",
  "slug": "shi-jian-lun",
  "version": 1,
  "reading": [
    {
      "title": "先抓住实践",
      "content": "……"
    }
  ],
  "difficulty": [
    {
      "wrong": "常见误读……",
      "correct": "正解……"
    }
  ],
  "dialogue": [
    {
      "title": "它在回应的问题",
      "items": ["……", "……"]
    }
  ],
  "action": [
    {
      "title": "实验一：做一次小型实践记录",
      "content": "……"
    }
  ],
  "further": [
    {
      "title": "推荐阅读一",
      "content": "……",
      "href": "../..."
    }
  ]
}
```

说明：

- `version` 用于以后平滑升级 schema
- `reading` / `action` 可用统一条目格式
- `difficulty` 保留正误对照结构
- `dialogue` 可以允许 `items` 数组
- `further` 可带 `href`

如果未来 `visual` / `puzzle` 也要数据化，建议单独再加对象字段，而不是现在先把它们硬塞进通用数组模型。

## 六、页面接入建议

不建议一上来就让 HTML 壳完全空心化。

推荐顺序是：

1. 先稳定 `data-article-json` 正文链路
2. 再让页面可选接入 `data-study-json`
3. 只先替换轻结构 Tab
4. 复杂布局块继续保留在 HTML

推荐接入方式：

```html
<body
  data-category="philosophy"
  data-article-json="../../../data/articles-json/Mao/★★★★★/shi-jian-lun.json"
  data-study-json="../../../data/study-json/Mao/shi-jian-lun.json">
```

这样可以保持：

- 正文渲染器只关心正文
- 精读渲染器只关心精读块
- 两层独立失败、独立回退

---

## 七、为什么分两个 JSON 比并成一个更稳

### 1. 修改风险更小

改读法提示时，不碰正文 JSON。

### 2. 校验逻辑更清楚

- 正文校验：段落、章节、源路径、mentor/star/slug
- 精读校验：Tab 条目完整性、文本字段、链接字段

### 3. 推进节奏更灵活

可以先完成：

- 29 篇正文 JSON 化

再逐步完成：

- 重点文章的精读 JSON 化

不会互相卡住。

先把《实践论》的页面壳、公共 CSS、正文链路彻底稳定。

## 九、当前决策建议

如果现在就要做决策，我的建议是：

> **有必要为精读层预留 JSON 化路线，但不要与正文层混一个文件；也不要现在立刻全站推广。**

对应执行建议：

1. 保持 `articles-json` 只做正文层
2. 预留 `study-json` 作为精读层
3. 只先结构化轻内容 Tab
4. 把《实践论》作为唯一首个 `study-json` 试点
5. 试点通过后，再扩到其余文章
